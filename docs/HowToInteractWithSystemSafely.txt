Both are instances of the same move: you can't verify the kernel boundary, so you relocate the unsafety and shrink what has to be trusted. The design space:

1. Localized escape hatch + safe wrapper — Rust's unsafe. Anyone can open a hole; the discipline is that the hole is small, audited, and wrapped in an API that upholds invariants for callers. TCB is diffuse (every crate's unsafe blocks) but the compiler tells you where to look.

2. Single trusted broker at the syscall edge — Fil-C. User code has no escape hatch at all; pointers carry InvisiCaps (bounds + permissions in a shadow region), and the only unsafe code is libpizlo, which owns the syscall and thread primitives and validates buffers against their capability before handing raw pointers to the kernel. Interop with non-Fil-C code goes through explicit zunsafe_call/zunsafe_fast_call. Tiny, fixed TCB — but you pay perf and must recompile the world.

3. Managed-runtime broker — JNI, cgo, P/Invoke. Same shape as #2: the runtime owns memory and the FFI stub is the only unsafe path. Extra wrinkle is GC interaction (pinning, handles) rather than bounds.

4. Hardware capabilities — CHERI. Provenance and bounds enforced by the CPU, so they survive across the kernel boundary rather than stopping at it. Removes the need for a language-level hole; needs the hardware.

5. Isolation instead of verification — put the risky code in its own address space or sandbox (WASM/WASI, RLBox, seccomp, separate process + IPC) and let it be unsafe. You don't prove correctness, you bound the blast radius. This is the only option when the code is a third-party binary you can't recompile.

6. Prove the hole — verify the unsafe layer once: seL4, RefinedC, Verus, or lighter-weight Miri/Kani/sanitizers on Rust's unsafe blocks. Converts "trust me" into "checked", at proportional cost.

7. Type the resources, not just the memory — OwnedFd/BorrowedFd, linear/affine handles, session types on protocols. Doesn't address memory safety but closes the other class of bugs that lives at that same boundary (double-close, use-after-close, TOCTOU).

The useful axes for choosing: how big is the resulting TCB, who's obligated to audit it, whether you can recompile the dependency, and what runtime cost you'll accept. In practice people stack them — e.g. verified-ish Rust wrappers around a seccomp-confined process.
