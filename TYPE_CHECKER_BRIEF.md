# A type checker for p2w — project brief

**The ask:** design and build type inference for a Python subset that compiles
to WebAssembly and to bare metal, where **the quality of the error messages is
the research contribution**, not a nicety bolted on afterwards.

This is written to be read by someone deciding whether to take it on. It says
what exists, what is decided, what is theirs to decide, and what "done" means.

## Why it is interesting

The field has split into two literatures that barely cite each other.

**Programming-languages research treats type errors as a localization problem**
— which sub-expression should be blamed? SHErrLoc (TOPLAS 2017), counter-factual
typing, and "Learning to Blame" (OOPSLA 2017), which trains on pairs of
ill-typed student programs and their fixed versions and reaches 72% top-1
against the OCaml compiler's 44%.

**Computing-education research treats them as a communication problem** — what
words work? Becker et al.'s ITiCSE 2019 landscape survey, and Santos & Becker
(UKICER 2024), who ran 106 participants across six buggy programs and found
that **handwritten explanations beat both LLM-generated and conventional
compiler messages**, on time-to-fix and on preference. GPT-4 won one task of
six. Students *preferred* the LLM messages while being no faster with them.

**Helium (Heeren, Hage & Swierstra, 2003) is the only project that did both** —
a Haskell compiler for beginners that split inference into constraint
*generation* and constraint *solving* so message quality became a property of
the solver, and added **type inference directives**: externally supplied rules,
including "sibling functions" that declare which functions beginners confuse so
the solver can try one as a fix. It worked, it was never adopted widely, and
nobody continued it.

So the opening is not "nobody has written good type errors." It is that
**nobody has built a compiler where pedagogy is a first-class input to the
inference engine, for a language children actually use.** Every ingredient has
been validated separately — the mechanism (Helium), the content strategy
(handwritten beats generated, measured), the implementation route (see below),
and the data. Nobody has assembled them.

Full survey with citations: [`PRIOR-ART-TYPES.md`](PRIOR-ART-TYPES.md).

## What already exists

You would not be starting cold. Deliberately, none of it is a half-built type

have to argue with it before replacing it.

One piece of scaffolding is explicitly yours to demolish: `compile_to_llvm_ir`
currently runs the WASM generator as a checker (discarding the WAT) so both
targets reject the same programs. The checks it borrows — literal string
arithmetic, mixed comparisons, annotation misuse — live inside `codegen`'s
`type_of`, and extracting them into your standalone front-end pass is the
first concrete milestone: the day it lands, that double-compile disappears.

**What the crate actually contains**, since "33k lines of compiler" would
overstate it: roughly **20k lines compile Python** (lexer, parser, hoist,
codegen, the LLVM backend, the component converter, reuse analysis) and
roughly **12k are analysis built on the same AST** — an interpreter and stepper
for the debugger, lints and their fix ladders, variable-role classification,
Blockly round-tripping, concept evidence. **You would be working in the first
20k.** The rest shares the AST, which is why it lives here, and is worth
knowing about mainly because a change to the AST touches it.

That is ~33k lines of Rust with **one runtime dependency**, 548 tests,
plus a native run-oracle of ~200 cases. MIT.

## What you would own

**Type inference for the subset, and the errors it produces.** Concretely:

1. **Inference that does not tax beginners.** `x = 5` must keep working;
   annotations are how you *say what you mean*, learned later, never a fee.
2. **Errors that point at the cause, not the symptom.** *"`total` is text
   because line 3 gave it `input()`"* beats *"type mismatch at line 40."* This
   is the part with the research contribution in it.
3. **The messages carry a fix ladder** — question, hint, fix — matching the
   existing `lint::Scaffold`.

### Requirements, not design

**How you infer is yours to choose and defend.** Constraint-based in the Helium
style, Datalog over a fixpoint, Cartesian Product Algorithm as Shed Skin uses,
plain Hindley-Milner — all are defensible and the oracle corpus does not care.
A student who chooses owns the work in a way one implementing someone else's
sketch does not.

Two facts that should inform the choice rather than make it:

- **Whole-program analysis is cheap here.** It is normally rejected for
  breaking separate compilation, and there is no separate compilation — one
  program, in a browser, no linking model.
- **Monomorphisation is already needed.** Unboxed `list[i64]` on the
  microcontroller target means specialising per type regardless, so the
  polymorphism answer and the memory model are entangled.

And one constraint that is not negotiable: **the checker must live in the
shared front-end.** Today's type-ish checks live in the WASM backend, so the
native backend does not get them — measured, and it accounts for most of the
14 remaining divergences.

## Decisions that are not yours

Five questions in [`tests/oracle/open-question/`](tests/oracle/open-question/)
are pedagogy, and Jason answers them: may a name change type; what is a mixed
list; how polymorphic is an unannotated function; what does a function that
sometimes returns nothing return. **Your job is to build what the answers
imply**, and to say which answers would be expensive.

## What done looks like

**`the_remaining_gap_is_exactly_what_we_think_it_is` fails.** That test in
`tests/oracle.rs` asserts the `must-reject` programs still compile. When
inference lands it fails, naming exactly which cases moved — and each one's
message gets read for whether a twelve-year-old could act on it before it is
promoted.

That is the whole acceptance criterion, and it is already written down and
running.

## Publishable angles

- **A before/after corpus.** The IDE observes student programs before and after
  a fix — the exact training data "Learning to Blame" used, for a language
  nobody has this for. (Consent and FERPA get settled before any collection.)
- **Derivation-carrying errors** — reporting the chain, not the symptom.
- **A controlled comparison** against the Santos & Becker protocol: authored
  ladders versus generated explanations versus conventional messages, in a
  compiler where all three can be emitted for the same program.

## Constraints worth knowing before you say yes

- **Both targets or neither.** A feature that works in the browser but not on a
  microcontroller means a student's program compiles at school and fails on
  their board.
- **The subset is a security boundary.** No dynamic name resolution — no
  `eval`, no computed `getattr` — permanently, because it is what keeps "this
  program reaches no host function outside the whitelist" decidable. `p2w check`
  already emits that manifest.
- **Every p2w program is valid Python.** Not the reverse. Restricting is free;
  extending beyond Python is not.
- **If you cannot write the error message, the feature is not understood well
  enough to ship.** This gate has caught more bad ideas than the other three.
